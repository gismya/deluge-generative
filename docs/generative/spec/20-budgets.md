# 20. Budgets and measured facts

Part of the [Generative mode spec](../spec.md). Section numbers are shared across all files.

Measured on a real OLED Deluge unless marked.

| Fact | Value |
|---|---|
| CPU | one Cortex-A9 at 400 MHz, cooperative scheduler. Ticks run inside the audio routine, which has about 2.9 ms of buffer (128 samples at 44.1 kHz) |
| Per-tick work | keep it in the tens of µs, with no card access and no allocation (estimate) |
| Task runs | keep each well under 3 ms, or split and yield. State read by the tick path must be consistent across yields |
| Voice starts | 4 per render window, 1 under heavy load. Extras wait one render: the audio routine targets 1.45 ms and is at most 2.9 ms. Above about 215 BPM a tick is shorter than a render, so the per-tick budget no longer holds. No fixed voice cap; culling is driven by CPU load |
| Fast heap free | 1002 K with no song; 749 K with a typical song; 694 K with that song plus a Perform roster playing (RelWithDebInfo, Release has about 46 K more) |
| Two songs in RAM | 591 K free at the swap with two typical songs, 273 K with two heavy ones (largest block 148 K). No late renders |
| Perform roster | about 162 K for the largest roster: 11 drum and 4 FX lanes at about 8.1 K plus 4 synths at about 10 K. Two rosters are about 323 K, which fits next to a heavy song (273 K free with two heavy songs is the closest measurement). Perform's song and the Generator blocks aren't in this figure yet |
| Steering log | one fixed 128 KB buffer in SDRAM, allocated on Perform entry ([§17.2](17-capture.md#172-the-steering-log)), not fast heap. A piece header is about 5–6 KB for the largest roster |
| Steering queue | 64 commands, fixed, in the Perform driver ([§2.6](02-architecture.md#26-steering-into-the-core)) |
| Kit lane | about 8.1 KB fast heap plus the sample in SDRAM. 10–15 ms per cold lane while playing; a 12-lane kit under 0.2 s |
| Synth preset load | 5.3 ms, 10 K fast heap |
| Entering Perform | 67 ms while playing with 4 lanes and a Bass |
| Silent incoming Kits | linked next to a playing heavy song, an 11-lane Kit costs 59 µs and a 4-row FX Kit 42 µs per 128-sample buffer: about 3.5% CPU together, with no late renders ([Measure silent incoming Kits and retiring Outputs on a Deluge][t83]). The cost is per render, so it rises when renders are short |
| Linking an incoming roster | 6–7 ms for three Outputs. The largest single link (clip, NoteRows and Output, no yield) took 1.6 ms. No late renders |
| Freeing a retired Output | `deleteClipObject` with `InstrumentRemoval::DELETE` while playing: 11-lane Kit 18–24 ms in 67 yields, FX Kit 6–10.5 ms in 21, Synth 1.7–3.6 ms in 5. At most 0.93 ms between yields, no late renders. The Output stays in the render list for about one yield per NoteRow first ([§12.9](12-runtime.md#129-instances-and-the-transition)) |
| Compose song | measured with a clip per part per Section occurrence: 1.7 MB for 4:00, 4.7 MB for 20:00, 15.7 MB for 60:00. Clip setup is 67–75% of it, about 130 K per occurrence (about 6 K per kit row, 11 K per synth clip). Notes are about 30 B each. So [§15](15-compose-output.md#15-compose-output-shape) uses one clip per part: about 0.7 MB for 4:00 and 1.8 MB for 20:00 (estimate). Freeing the current song doesn't help the fast heap: song structures are `allocMaxSpeed` and fill it first. XML parsing is 2–5× slower while audio runs |
| Saving and loading songs | a 1.0 MB file saves in 0.36 s and loads in 2.0 s. A 10.1 MB file saves in 3.4–7.55 s but fails to load on an empty Deluge with `FILE_CORRUPTED`, so Capture splits long pieces ([§17.5](17-capture.md#175-song-shape)) |
| Out of memory | once SDRAM is full, any `operator new` throws `BAD_ALLOC`, nothing catches it, and the device freezes with `TERM`. Compose and Capture stop at an SDRAM reserve, 512 K to start ([§15.9](15-compose-output.md#159-memory-and-failures)) |
| Pad redraw | 21–22 ms of UART per full redraw, shared with the OLED. Pad sends defer behind OLED updates. Any main-pad change sends all of them (`sendOutMainPadColours`), so a row mask saves render time, not UART. The SONG page in delugemu: 100 main redraws in an 8-bar Techno phrase with nothing queued (under one per 16th), 139 with queued actions blinking (about 9.4 a second; the ceiling is about 45) |
| Arc plan | `Generator::planArc` (16 phrases, 2,048 steps for Techno) takes about 0.55 ms in delugemu, 1.3 ms the first time; not yet measured on hardware |
| OLED | 128×43 visible, 4 rows of 21 characters or a title plus 3 rows. Redraws at most every 10 ms. `OLED::setupSideScroller` doesn't scroll while playing; the Compose title scrolls the way the stock session view scrolls a long song name |
| Tempo | the hardware plays exactly the set BPM (130.0000 by the sample clock). delugemu runs about 0.5% slow |
| Stability | the POC's hook ran 31 minutes with no leak, drift, stuck notes or late renders, and followed swing and tempo changes exactly |
| `new` | global `operator new` and std containers use only a 2 MiB SDRAM pool and throw when full. The Generator doesn't use them ([§2.1](02-architecture.md#21-the-generator-core)) |
| Song loads | the "buttons and pads" task can run up to 20 ms without yielding during a song load |
| System clock | `getSystemTime()` reads about 0.8% short against real time |

The POC's core was about 1.65 KB of state (`sizeof(Generator)` 1664 B) with no allocation.

The M1 core is 16,208 B of state per Generator block on ARM (`sizeof(Generator)`, measured after the gestures and drift slice, #107, which gave a Drums part a control set per lane as well as its kit-wide one (20 sets of 22 B, each with its Throw state and its drift walk's points, kept so a step draws only when the walk passes a point), gave the event buffer room for 108 Control events a step, counted from the controls each kind of set can move, and moved the buffer's keep priorities into spare bits of each event (707 B less); it was 15,668 B after the transitions slice, #115, which gave the pending list a transition slot (12 B), the instance its start step (4 B) and the Arc a hold that waits for a new roster's Groove; it was 15,648 B after the fills slice, #103, which counted a note-off for every hit inside a step in the event buffer, 62 events or 1052 B more, packed each Loop line step into 2 B (384 B less) and gave each part's sounding and late-entry tables only its role's share of one pool (480 B less), with 4 B of fill state; it was 15,456 B after the CLIP page slice, #111, which gave the event buffer a Sound event per part in each of its two steps, the pending list a sound slot per part, and each part its last landed sound; it was 15,172 B after the Loop lines slice, #99, which gave each lane's pick the bar it began on and room for a pick that waits out a freeze, 8 B a lane, plus each part's Answer and freeze state; it was 14,608 B after the sound controls slice, #106, which added room in the event buffer for one step's Control events, 54 of them, and the 9 control sets' last-sent offsets; it was 13,612 B after the sidebar slice, #109, which gave the pending list a mute and a solo slot per part; it was 13,496 B after the section rules slice, #102, it was 12,260 B after the interplay and expression slices, #100 and #101, and 8480 B after the sounds slice, #104, moved the Recipe's sound picks out of the Generator's copy). The event buffer, sized part by part for the largest roster, is most of it: 12,176 B (761 events of 16 B). It holds a step plus the step still playing, each with every note's hits, a note-off for each hit inside the step, and a note-off for every note already sounding; only one of the two can be a bar line, so the re-strikes of late entry and the Section-line cut are counted once, and only the step being decided can hold Control events (each control each control set can move), since they play on its grid line. The sounding-note table and the late-entry table are 824 B each (one pool of 51 notes, each part given what the buffer counts for its role, for a roster with at most one Drums part), the pending list 328 B (27 commands of 12 B) and the Arc 72 B. Perform's two blocks take about 30 K of fast heap. The Current Recipe is 13,192 B in SDRAM (`PLACE_SDRAM_BSS`): the Recipe, its sound picks and the copy a genre pick stages (2.7 K each), and two palette overrides (3.9 K each), one in use and one staged. The sounds slice adds no internal SRAM. The Perform adapter's sound controls keep each piece's bound params (where each sits, its home and range) in 5.6 K of SDRAM (`PLACE_SDRAM_BSS`; 7.8 K before the homes slice, #112, found a patch cable by its source and destination instead of a pointer, and sized the list from the §11.2 table), sized for every control set moving every param it could. Sound re-rolls keep three sets of sound picks in SDRAM (8 K: the picks a preload rolls, those of each part's sound waiting for its line, and each part's previous sound) and, with transitions (#115), the pending Recipe and its sound picks (2.7 K), the roster a preload builds, and up to 24 retiring Outputs' handles twice over (the list and the free job's, 1.4 K and 1.3 K), all in SDRAM. A `static_assert` bounds the Generator block at 16 KB (H18).

**H1, measured** on the M1 skeleton (Techno, Drums with 4 lanes and a Loop Bass, RelWithDebInfo, 33.33 MHz OSTM count around each step decision in the tick, reported every 4 bars): at the default macros a decision costs 10.5–11.4 µs on average, at most 22–48 µs; with every macro at 50, 14–15.4 µs on average, at most 26–31 µs, with one 4-bar window at 53.6 µs. That is the "tens of µs" assumed, so the phrase-line fallback of [§12.2](12-runtime.md#122-when-steps-are-decided) isn't needed yet. With keyed pattern picks (#98): 12.7–13.1 µs on average at the default macros, at most 27–33 µs; with every macro at 50, 15.7–19.6 µs on average, at most 30–39 µs, and 76 µs in the 4-bar window holding a Drop, where every lane picks afresh and the Loop line is rolled. Later M1 slices (Release test-port build, every 64-step window of a session's Perform scripts): 24.7–25.9 µs on average and at most 42.7–84.8 µs in hardware run 2, before the Loop lines slice; with Loop lines (#99: mutation on the curve, an Answer draw at bar lines, freeze), 27.0–31.9 µs on average and at most 49–97 µs over 14 windows of `perform_skeleton.txt`, `perform_sidebar.txt` and `perform_song.txt`. The maxima over 90 µs fall in the first window after PLAY, as before, and in one window with macro turns. Still tens of µs. Re-measure as later slices add parts and layers.

**H2, measured** on the sound controls slice (#106: Techno, Release test-port build, `scripts/generative/perform_sound_controls_h2.txt`, reported every 4 bars as `gen_h2`). Measured over four sessions on one Deluge; a piece binds 27–28 params over 5 control sets (the Drums Kit's affect-entire params, the acid Bass, three FX rows). In the Intro, where Energy rises and Brightness, Decay, Drive and Space move together on 15–16 steps in every 4 bars, applying a step's Control events costs 25–27 µs on average and at most 32 µs in the tick, for about 20 params (two 64-bit divisions per param had made it 33 µs; the Cortex-A9 divides in software). The ramps' render cost was found by playing the same piece twice, with the test port's `hold ramps` dropping every Control event the second time: per 128 samples, the Intro renders 80–119 µs slower with ramps (10–14%). A Break, where the sound stays shaded with nothing ramping, renders 62 µs slower (9%), so most of that is the shaded sound (longer releases), and the ramps themselves cost about 20–60 µs per 128 samples, 1–2% of the CPU. A Groove at home renders the same within 1 µs, so a param left flagged as interpolating after its ramp ends costs nothing measurable. The slowest render was 0.41 ms either way. The worst case, every bound param rewritten on every step (the test port's `hold stress`: all 28 params ramping halfway up and down their ranges in turn), costs 22 µs a step in the tick and about 280 µs per 128 samples in the render against the same piece with no ramps, in the Intro and the Groove alike: about 10 µs per 128 samples, 0.35% of the CPU, for each param ramping all the time, with the slowest render at 0.59 ms. So at the macro layer's pace the ramps cost little, and no phrase-line or coarser grain is needed. Drift and gestures (#107) move more params more often: budget about 0.35% of the CPU per param they keep ramping, and re-measure with them.

**H9, measured** on the M1 runner (entry as a modal runner job, timed from the OK press to Perform's song swapped in): on hardware (Release, the `gen_entry done` event), over the blank song leaving lands on, 129–172 ms over two runs (136–172 ms in #168's, 129–152 ms in #169's). Every entry reads its samples from the card: leaving empties the sample cache (below). Earlier, with samples still cached between entries, the RelWithDebInfo runner took 25 ms with the user's heavy song Ttt playing (531 K of fast heap free before entry), from a fresh boot, and 23–35 ms cold over the boot song. The roster was M1's Techno at the time (an 11-row Kit with 4 sampled lanes, and a synth Bass), so re-measure once Techno has its full roster. BACK 5 ms into a cold build cancels it, and the job has unwound 12 ms after the OK. Leaving takes 16–17 ms, 0.7–1.2 ms of it (`gen_left`'s `delete_us`) deleting Perform's song and every unused cached sample. With a large sample cache it is no slower: after loading Ttt (`perform_leave_heavy.txt`, #172's run: 3.4 MB of Ttt's samples still cached when Perform's entry deletes the song), leaving took 16 ms, 1.5 ms of it deleting.

**H16 and the transition, measured** on the transitions slice (#115: Techno, Release test-port build, one load, `perform_transition.txt` and `perform_transition_input.txt`). No render culled a voice in any 4-bar window of the session (`gen_h16 culls=0`), around each transition's Drop, seam and cut line included, so neither Kick nor Bass was culled; the slowest render in a window was 193–422 µs (no late renders). A Regenerate's preload (roll, every sound re-rolled away from the playing one, three Outputs built and linked) took 178–224 ms; a BACK tap cancelled one 115 ms in. During preloads every press was taken within 9 ms of being due (`input_lag`), and gold-knob edges kept their 160 ms pace (no card wait held one back). The start step's work in the tick (the roster swap, the Current Recipe, binding the sound controls) took 90–93 µs. H1 stayed tens of µs: 28–39 µs on average per 64-step window, at most 114 µs, in the window holding a transition's start step. A retiring Output still sounding at its cap faded over a beat and was freed. Over each enter, Regenerate and leave cycle both heaps came back to the byte.

**H17, measured** on the MIDI slice (#117: Techno, `perform_midi.txt`, MIDI follow's default mappings, feedback at the HIGH rate, 40 ms) on hardware (Release test-port build, b395ec5d0). Feedback sends a value only when it moved since it was last sent (§13.7), so while a piece played with ACID focused the steady windows sent 361–412 B a second on DIN's 3 B a CC, 12–13 % of the 3125 B/s link, at most 7 CCs a pass; later windows sent 14–109 B/s. A context change (a focus, entry) sends every mapped param and the macros in one pass, 84 CCs (252 B): its window sent 600 B/s, as stock sends one. delugemu gave 431–568 B/s, at most 8 CCs a pass, the same with every sound-control param re-ramped each step (`hold stress`). Stock's own automation feedback re-sends every automated param each pass, unfiltered.

**Leaving frees what entry built.** After an enter/leave cycle the internal and external heaps are exactly where they were before entry. The first cycle after boot is the exception: it costs 320 B of internal heap once (the sample cache's bookkeeping), and on hardware it leaves 296 B more external heap free than before, since that leave also deletes the samples cached before entry. Two rules give this:
- Leaving deletes every audio file no song uses, before it builds the blank song: the samples Perform loaded, and the previous song's cached samples too. Stock firmware keeps unused samples as a stealable cache, which still holds heap, and each entry picks new sounds. The cost is card reads: entering again, or loading the old song back, reads its samples from the card.
- Building the blank song leaks nothing: a stock Browser leak lost 96–104 B of external heap on every SHIFT+LOAD → NEW (`docs/upstream-candidates.md`).
