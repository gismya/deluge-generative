# 21. Testing and CI

Part of the [Generative mode spec](../spec.md). Section numbers are shared across all files.

### 21.1 CI

- Only `tests.yml` runs, on every PR (milestone branches too): x86 unit tests, ARMv7 under QEMU user mode and the `generative-rules` hooks, about 2.5 min, each job with a timeout. `test-results.yml` publishes its results.
- Every other workflow file is deleted, not disabled: `backport-from-issue`, `backport`, `beta-build`, `build`, `nightly-build`, `pr-build`, `release-build`, `publish`, `clang-tidy`, `format-check`, `deploy-website`, `label-issues`, `label-prs` and `sync-labels`, plus the `.github/scripts` and labeler config files only they use. autofix.ci has no file in the repo and stays. Upstream merge conflicts on deleted files are solved as they come.
- No branch protection. `AGENTS.md` gets a rule: don't merge a PR while **Run tests** is red.
- Hardware is never in CI.

### 21.2 Harness

- The Generator's tests are another target in the `tests/` CMake tree. CI runs them in the x86 job only, not `tests/qemu`. Locally they build natively on the Mac with dbt's cmake and Apple clang. The target builds with `-fsigned-char` like the firmware, and CI runs it with `-fsanitize=signed-integer-overflow` (ADR 0004). It also defines `GENERATOR_TEST_SEAMS`, which the firmware never does, for harness-only hooks in the core: one plays a flavour the core has no code for yet, so a spec can fill the largest roster before every flavour exists.
- **Specs** hold invariants and equivalences. The invariants come from the first slice. Each equivalence comes with its driver: Perform against Compose in M3, Capture replay in M4:
  - every pitched note is in scale and in its Register;
  - every note-on gets a note-off;
  - voice starts per step, reported against the 4-per-render budget rather than failed, since the firmware defers extra starts (§23.14);
  - interplay rules only target earlier parts and earlier Drums lanes ([§5.5](05-parts-and-lanes.md#55-interplay-rules));
  - every Motion curve table matches its formula, R and start ([§3.5](03-recipe.md#35-motion-curves));
  - every Register span is at least 12 semitones wide, and an Arp part's span holds its widest pool entry's octave range ([§7.3](07-pitch.md#73-register));
  - stepping back to a take within one pick replays that take's line as it unfolded before, under the same macros ([§6.6](06-randomness.md#66-takes)), and an Arp's notes don't shift when Density thins it ([§8.1](08-rhythm-and-expression.md#81-onsets-and-density));
  - an untouched Perform driver run matches a Compose run ([§6.8](06-randomness.md#68-perform-and-compose-agree));
  - a Capture replay matches the live steered run ([§17.1](17-capture.md#171-what-it-is));
  - a note held across a Section line gets a note-off on the line and is re-struck by late entry ([§12.5](12-runtime.md#125-mute-gate-and-note-offs)), except a note a Sustain that holds across Section lines keeps at its pitch, which plays on with no note-off and no note-on there ([§5.2](05-parts-and-lanes.md#52-flavours));
  - every ordered pair of built-in genres changes in each of the three transition styles: every outgoing note ends, the incoming roster's notes are in its scale and Registers, nothing overflows, the tempo glide arrives where the new roster starts and swing switches on its start step. Each case plays only until the new roster's first phrase ends, so the whole matrix adds under 15 s to the harness run; past that, each genre changes in and out against two neighbours instead of all;
  - no step overflows the event buffer or the sounding-note table ([§2.7](02-architecture.md#27-buffer-sizes-and-overflow)), and a Bass or Lead note overlaps only the next onset's ([§8.5](08-rhythm-and-expression.md#85-lean), [§8.6](08-rhythm-and-expression.md#86-slide)).

  Equivalence checks compare two live runs, so they store no file. Perform against Compose (`compose_driver_spec`) runs every genre's default Recipe, and at Motion 0 and 100, with re-rolled takes and with a sample Riser, and compares everything before the Outro's first step: the notes exactly, and each automation lane's nodes against the value Perform reaches on each step line, within the thinning's tolerance, and within the kept points' tolerance in a bar where Perform's value doesn't move ([§15.6](15-compose-output.md#156-automation)). They run the portable Perform and Compose drivers with recording sinks ([§2.5](02-architecture.md#25-portable-drivers-and-firmware-adapters)). The Capture check (`capture_replay_spec`) runs the portable Perform driver with a steering script, takes the log it wrote, and replays that log through the portable Compose driver: every command kind, a transition with its tempo glide (a Build into a Drop and a hard cut), a re-roll, a dropped swap, a key change, a restart, a log cut short, and a force, End or Build pressed (and cancelled) at steps across every genre. Each piece's notes match its instance's exactly before its span's last decision; an untouched run with End where Compose queued it gives Compose's song.
- **Goldens** catch change: Recipe + seed + takes + steering script → a text dump. Before v1 there is **one golden per signed-off genre**: its default Recipe at a fixed seed, short. Each Techno subgenre has one. An M2 genre (Ambient, Psytrance, Dub, House) gets its golden and its `kPinned` steering fingerprint when the player signs it off on the Deluge ([#133](https://github.com/gismya/deluge-generative/issues/133)), not when its slice lands, so tuning it needs no version bumps. Until then nothing pins its stream, and a change to shared code can move it unseen: that is accepted while it is tuned. The fuller set (a default Recipe per genre for a full Arc cycle, plus steering cases such as macro sweeps, force and hold, Fill, take re-roll and step back, Regenerate, genre change, key change and freeze) comes after v1, or earlier when a bug escapes.
- **Retuning on purpose:** one local command regenerates the goldens, committed with the retune (**A retune** below). Review is the text diff.
  - **The goldens.** `tests/spec/generator/goldens/<genre>.txt`, one per signed-off genre, checked by `golden_spec`: the default Recipe (the genre's new Recipe from entropy 0) at seed 1 for 16 bars from SHIFT+PLAY, so the Groove at its default macros; one event per line (tick, bar.beat.16th, part, then the lane or note name and what it does, Control events included). Its header holds the genre's version and its stream fingerprint over 60 pieces with random macros, scales, keys and seeds, two thirds of them with an Intro: the golden pins the whole stream, the dump shows the default Recipe as text. **A retune:** in the genre's table (`src/deluge/generative/core/genres/`, `techno.cpp` for a Techno subgenre), raise its `genre.version = N;` line (after `subgenreOf(kTechnoParent)` in a subgenre) to N + 1, run `./dbt test --generator --update-goldens`, copy the steered fingerprint `steering_fingerprint_spec` prints for the genre into that spec's `kPinned` (below), commit the table, the goldens and `kPinned` together, and name the genre in the commit (`Retune techno-acid (version 2): …`). Nothing checks the commit message: the command only prints the retuned genres for it. The rule is `scripts/generative/goldens.py`: a golden whose stream changed needs its genre's version above the one at the merge base with the branch's base (the open PR's base when `gh` knows it, else the branch's upstream on origin when that's another branch, else `generative`: `scripts/generative/pr_base.py`), fetched from origin first so a stale local branch or an old fetch never sets the merge base, so one bump covers every retune of that genre on a branch. A version below the base's fails whether or not the golden changed: versions only go up. A golden the base hasn't yet counts from the commit that added it. The command, `check_all.py` and CI (the generative-rules job, against the PR's base) all check the rule, the command whenever it wrote a golden. CI's checkout is shallow and can't find the commit that added a golden, so there a golden the PR's base hasn't is new and unchecked; the command and `check_all.py` check it. An update never writes a dump that lost events. A golden whose `format` line went up (a change to the dump itself, its seed or its length; none is format 1) needs no bump, unless its `fingerprint` line changed while the text in its parentheses didn't: the fingerprint doesn't depend on the dump, so that is a retune. A new format is refused while the genre tables (the `.cpp` and `.h` files in `src/deluge/generative/core/genres/`) differ from the base: a retune the fingerprint doesn't see would pass as the new format, so the format bump lands on its own. A golden that is gone since the base is reported, and `golden_spec` checks that every signed-off genre has one. `golden_spec` pins no subgenre's table, so a retune needs no edit to it. `steering_fingerprint_spec` pins each subgenre's stream under steering (mutes, solos, held fills, a force, End), which the goldens play without: a retune fails it too, and its failure prints the new fingerprint, which the retune copies into the spec's `kPinned` (the command reminds it). A retune of a genre the probe scripts' Recipe fixtures name (`scripts/generative/fixtures/recipe_load/`, Acid techno) also bumps the fixtures meant to be today's and the scripts' version expects: `test_recipe_fixtures.py` checks them against the golden. A retune that moves a fact §4.5 states (tempo range, scales, roster) also edits §4.5 and the subgenre's identity spec, which mirrors it.
- **Rough render:** an offline, deterministic render of a Recipe to a WAV, a Standard MIDI File with one track per part, and a text piano roll. It uses our own small voice code (one subtractive voice plus a sample player for kit rows, which follows the firmware's repeat-mode rule: a sample of 2 s or more stops at its note-off, a shorter one plays out, [§10.4](10-sounds.md#104-building-a-kit-in-code)) and reads samples from `pack/` and a local card-shaped folder. Parameters it doesn't model are ignored with a warning. Renders are made locally and never committed. The MIDI file's last track, THEORY, holds as text what the notes don't show: the Recipe, each part's and lane's Density gate and interplay rules, the key, chord and effective macros as they change, and which hits are Ornaments (so a ratchet counts as one onset). For the theory review (§21.5) the render can play one Arc cycle (`--end-after-drop`: End armed on the Drop, so the Outro follows its phrase; `--end-after-drop N` on the Nth Drop, `--end-at-bar BAR` on a bar, as a delugemu capture given the same flag holds the End pad) and write the MIDI file alone (`--midi-only`). `--mute PART` (a sidebar row, as delugemu capture's `--mute`) leaves a part out of the WAV from step 0, as a Perform mute does, for an isolated clip: the Generator plays as without it, and the MIDI file and piano roll keep every part.

### 21.3 delugemu (local only)

- Use [SynthstromAudible/delugemu](https://github.com/SynthstromAudible/delugemu). It runs headless, scripted and deterministic in icount mode (`-icount shift=2,sleep=off -S` with `run_until`). The factory card is a prebuilt `mksd.sh` image at `~/source/delugemu-sd`.
- A probe script that needs another card names an overlay folder in its `# needs: card fixtures/<script>` line (`perform_sounds_override.txt`, `perform_sounds_fallback.txt`). `test_port_emu.py` reads that line and puts the folder on each boot's clone of the factory card: the steps in its `card.txt` (`remove PATH`, `copy FROM -> TO` from the repo or the card), then its own files. `fat_image.py` writes the FAT32 image directly, with no mount, sudo or `._*` files.
- A script in the repo runs **smoke checks** against a local `./dbt build release`: boot; Perform starts and plays N bars (non-silent, no freeze); Compose builds a song, saves it and reloads it; Capture writes its songs; a Recipe file round-trips. The checks are functional only, with no audio hashes. `gen_emu.py smoke` plays Perform on the plain build, leaves with Capture (`LEAVE, KEEP: LAST`), reloads the saved Capture song and checks it plays, and reads the new song file off the card clone (`golden_song.capture_song_summary()`) to check it holds valid clip instances and notes. The Compose and Recipe-file checks run on the test-port build, in the firmware check's boot (below), which needs the test port to read the files back.
- **Firmware matches the harness:** render the golden case through Compose in delugemu, read the saved song's notes back into the same text dump, and diff it against the harness golden. This is the only end-to-end proof that the firmware plays what the harness tested. `gen_emu.py golden` runs it on the test-port build with Acid techno's golden, the genre `golden_compose.txt` picks, in one boot of about 10 s with the Compose and Recipe-file smoke checks. Under the test port's `hold golden`, a genre roll makes the golden case (`golden_case.h`: the default Recipe at the goldens' seed, takes 0) and Compose starts in the Groove, as the golden plays from SHIFT+PLAY (`ComposeDriver::begin()`'s `skipIntro`, which only this check sets). The Compose screen's SAVE writes the Recipe file and `check recipe *` reads it back, BUILD composes, and the song is saved and loaded back. The script then reads the song and the Recipe file off the card clone (`golden_song.py`): the Recipe file must hold the golden's genre, version, tempo, swing, key, scale, macros, seed and takes 0, and the song's notes must be the golden's note lines. Compose writes no muted note, so those leave the golden's side, and an ornament is a plain note. The golden ends at its last line, where Perform's stop ends what still sounds, so both sides keep the notes that start more than `kMaxLean` before that tick, cut there. `compose_driver_spec` checks the same rule in the harness for every golden.
- **A Recipe and Seed for the next roll** (seam S7, gismya/deluge-engine#21; test builds only): `next recipe` lines on the test port set the Recipe and Seed the next roll takes, one field a line, so a tool plays a given Recipe without a build of its own. `genre NAME` (`techno-dub`), `seed N` and `entropy N` (0 to 2^32-1: the facts and the sound picks roll from it), `macro M POINTS` (M 0–3 in Macro order, 0–50), `tempo HUNDREDTHS` (of a BPM), `key 0-11` (0 = C), `scale N` (a `Scale` value, 0–11), `swing -49-49`, and `part P PATH` (0–5, by roster index) or `lane L PATH` (0–14, in `Lane` order) for a sound pick, the path being the rest of the line. They mirror `RecipeOverrides` plus sound picks (`NextRecipe` in `recipe_overrides.h`). A field left out keeps what the roll gives it: the genre the roll is for, fresh entropy and seed, an empty pick rolled from the palette. The next roll takes them, and sends `gen_next_recipe taken`: entry into Perform or a genre pick (`CurrentRecipe::rollFromGenre()`), or a Regenerate, the Compose screen's or Perform's, which also covers a genre change in Perform (`rollPending()`). A Regenerate or a genre change in Perform keeps its own genre, and in Perform the live macros win at the handover. A roll that fails or is cancelled leaves them for the next one. Rolls after that draw fresh entropy again. `next recipe clear` forgets the fields, and so does `reset recipe` (`start_state`). `perform_next_recipe.txt` checks them.
- **Genre changes:** each genre has one probe script that changes into it and back out in all three transition styles in one boot: an M2 genre from the M2 genre before it (Ambient from Acid techno), and Psytrance into Dub for the long tempo glide.
- **Hardware-only expects:** the probe scripts run delugemu in real time, and under host load it renders slower than real time, so it culls voices, sounds fewer and measures the host's clock off its own (#417). An expect that pins such a figure starts with `hardware_only`: `hardware_only expect event /^gen_h16 culls=\d+ culled=\S+ voices=[1-9]/ within=20`. On the Deluge it runs as a plain expect. Under delugemu (`test_port_emu.py`) an `expect event` waits for an event of its kind only (any `gen_h16`), so what follows waits as long as on the Deluge, and a `no_event` or state expect is skipped; either way its figure counts as a hardware-only skip, in the script's result line and in `check_all.py`'s table. The skip count overlaps the expects' count: an `expect event` one still runs (its kind) and counts as an expect too, a skipped one doesn't. The figures (`covers.TIMING_FIELDS`): `gen_h16`'s `culls=`, `culled=`, `voices=` and `render_max_us=`, `gen_h1`'s `mean_ns=` and `max_ns=`, `gen_h2`'s `mean_ns=`, `max_ns=` and `render_ns=`, `gen_audio`'s `underruns=` and `margin_min_us=`, `gen_audio_late`'s `underruns=` and `run_max_us=`, `gen_audio_ui_timer`'s `over_2ms=` and `run_max_us=`, `gen_ext_tempo`'s `bpm=`, `gen_midi_feedback`'s `ms=`, `bytes_per_s=` and `peak_pass=`, and the `us=` of `gen_transition`, `gen_arcplan` and `gen_log_piece`. `covers.py --check` fails an expect that pins one to less than any value (`\d+`, `[0-9]*`, `\S+`, `.*` and the like, also inside a capture group) without `hardware_only`. No load-proof event says "it plays" (no note event), so the Break's and Drop's `voices=[1-9]` became hardware-only too: under delugemu the `gen_h16` report still has to come.
- **Pinning:** the repo records the delugemu commit the checks last ran with. The script warns when the installed bundle's `VERSION` differs, and bumping the pin is a deliberate commit.
- Gotchas: one boot in three can come up blank, so the script needs a boot check and a retry. Under icount the virtual clock runs faster than real time, so waits count virtual time. pylib's `press` and `load_song` use wall-clock sleeps, so icount scripts use `run_until` plus `button()`. Check timing in ticks or MIDI, not audio.

- **Null guard (test builds):** a build with the sysex test port (`ENABLE_SYSEX_TEST`, in delugemu and on the Deluge)
  makes the first MB of the address space a translation fault at boot (`guardNullPage()` in `src/resetprg.c`). A read
  or write through a null pointer then data-aborts at once. Without it the Deluge reads whatever its empty CS0 bus floats
  to, so a null dereference crashes only sometimes, and delugemu never. To see where a fault happened in delugemu, run
  `test_port_emu.py --gdb PORT`, attach `arm-none-eabi-gdb` with `target remote :PORT` and `hbreak handle_cpu_fault`:
  r0 and r2 at the break are the faulting PC and the LR. Add `--gdb-wait` for a fault during boot: the CPU waits at
  reset until gdb continues it.

### 21.4 When agents run checks

These rules are in `AGENTS.md`:

- Harness tests and specs on every Generator change.
- delugemu smoke checks and the firmware check before pushing any change under `src/` that touches Generative mode.
- Hardware runs (the `deluge-hardware-test` skill, over the sysex test port) in the test plan for changes to UI, timing, memory or CPU.

`scripts/generative/check_all.py` runs these checks but hardware, and only those a change needs against its base (#314):

- the harness specs sanitized only (the plain run caught nothing the sanitized one missed; `./dbt test --generator` stays for iterating), `ctest -j` in both;
- the Python unit tests only for a change under `scripts/`, `pack/` or `src/deluge/generative/`, each file in its own process;
- the firmware builds and delugemu only for a change to a firmware input (`src/`, `lib/`, the root `CMakeLists.txt`, the linker script, the toolchain and its CMake file (`scripts/cmake/`), the dbt build tasks), to what the emulator checks run on (`gen_emu.py`, `test_port_emu.py`, `deluge_probe.py` and the modules they import, the delugemu pin) or decide what they run (`check_all.py`, `covers.py`), or to a probe script or what one covers;
- in delugemu, smoke, the firmware check (`gen_emu.py golden`) and `test_port_smoke.txt` always, plus each probe script whose `# covers:` paths changed (`scripts/generative/covers.py`): a file a covers line names or a folder or glob it names holds, the script itself or a file it includes, or a file every script depends on (`test_port_emu.py`, `deluge_probe.py` and the modules they import, the delugemu pin, the firmware's test port). A script with no covers line runs whenever delugemu does. A `src/` file no covers line names runs smoke, the leak check, the firmware check and `test_port_smoke.txt` only, and needs `--full` before its merge (below). `covers.py --check` (every run, and the unit tests) fails on a covers path that matches no file, on a `src/` file that sends an event a script expects or rules out, or builds the text of one (`covers.BUILDERS`: `queueTag()` in `queue_text.cpp` builds `gen_status`'s `>KEY`), but its covers lines miss, on an event expect that doesn't start with its kind (`force=B` matches inside any event; `/^gen_sidebar .*force=B/` names it), and on a builder gap: a kind a `TEST_EVENT("gen_x ... %s")` fills with no `covers.BUILDERS` entry, or a file sending `TEST_EVENT("%s", ...)` no `covers.RELAYS` entry names, on a timing expect without `hardware_only` (above), and on an orphan: a `scripts/generative/*.txt` that `check_all.py` neither runs nor lists as not run, that no script includes, and that has no `# runs-via: COMMAND` line naming what runs it (`golden_compose.txt`: `# runs-via: gen_emu.py golden`; #466). The leak check runs whenever delugemu does, with one warm-up and one checked cycle. The longest emulator job starts first, by the time it took last;
- `--full` runs every check and every probe script whatever changed. Whether the final run before a merge needs it is mechanical (`covers.full_rule()`, #417), and the table's first line says which rule applied: "needs --full: WHY" for a merge into `generative`, for a changed firmware input (`covers.FIRMWARE`: `src/`, `lib/`, the build files, the toolchain) no probe script's covers line names, or for a change to what the emulator checks run on or what picks them (`gen_emu.py`, `test_port_emu.py`, `deluge_probe.py`, their imports and the scripts they name, the delugemu pin, the test port, `check_all.py`, `covers.py`); else "covers pick suffices". A run with no merge base runs everything, so it counts as `--full`. Where the `--full` run happens: an agent on a milestone runs the default covers pick, and the orchestrator runs `--full` on the milestone branch after merges, outside the agent loops, and audits the results; a milestone's latest full run is clean before it merges into `generative` (`docs/agents/orchestration.md`, **Full runs**).
- Every real-time delugemu (the probe scripts, the leak check and the firmware check) takes a slot from a pool shared by every checkout on the host (`scripts/generative/emu_slots.py`: an flock on `~/.cache/deluge-generative/emu-slots/slot-N.lock`, so a crashed run frees its slot; `DELUGE_EMU_SLOTS`, default 6) and waits while it is full, first come first served (a run finds anyone waiting, it queues too): `--jobs` caps one run, the pool every run together. The icount runs (`gen_emu.py smoke`, `capture`) take none. A row that waited says how long, the table adds the waits up, and `python3 scripts/generative/emu_slots.py [--since S]` prints the slots held and the most held at once.

A hardware session runs `test_port_smoke.txt` plus the scripts `covers.py --hardware` picks for the change; the whole hardware set (`covers.py --hardware --full`) runs on a milestone's final run.

`deluge_probe.py session` guards the shared Deluge and its card (#464, #465):

- With `--no-load` it refuses (exit 1) unless `loaded.json` records a load of the calling checkout's `git rev-parse HEAD` (a load of `<sha>-dirty` counts as `<sha>`), checked before it takes the lock and again once it holds it; a missing `loaded.json` refuses too. `--force-build-mismatch` runs anyway, with a warning naming both SHAs. delugemu (`--udp`) isn't checked.
- It lists `SONGS/` and `RECIPES/` on the card before the first script and after the last, and prints each new entry's path. A new entry no script in the session declares fails the session (exit 1). A script declares what it may leave with `# writes: GLOB` lines, one glob each, from the card's root, matched without regard to case (`# writes: SONGS/GEN ACID TECHNO *`); an included file's lines count. It sees only new names in those two folders: a file overwritten in place, or one written elsewhere, passes unseen.

### 21.5 Genre tuning loop

1. **Harness rough render**: rhythm, harmony and interplay in stand-in sounds, with no firmware build.
   - **Theory review**, in each genre's slice: a script (`scripts/generative/theory_review.py`) summarises `generator_render`'s MIDI for the genre's default Recipe over a full Arc cycle at a few entropies (onsets by 16th position per lane and part, pitch classes against the scale, chords per bar, each part's range and its overlap with the others, notes per bar per Section, notes against each Density gate, each interplay rule's effect, velocity ranges). A fresh agent reads it against §4.5's brief and the genre's conventions. A clear fault is fixed in the slice; a judgement call becomes its own ticket for the player. It never blocks a merge.
2. **delugemu capture with the real sounds**, the main loop: a script takes genre + Recipe overrides + seed + length, then builds, captures and plays the WAV. A 60 s capture takes about 18 s on an M4 Pro, and the same seed before and after gives a fair A/B.
3. **The real Deluge**: sign-off, and how steering feels.

A tweak that changes a genre's event stream fails its golden ([§21.2](#212-harness)). Once it sounds right, retune it as [§21.2](#212-harness) says: one version bump, new goldens, the genre named in the commit.

Genre tables stay compiled in, so a tweak is an incremental rebuild. There's no dev-only card override.
