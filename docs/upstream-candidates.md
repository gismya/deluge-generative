# Upstream candidates

These are firmware fixes, made in this fork or found while working on it, that look better than upstream's code whatever Generative mode needs. Each one should be checked for an upstream PR to the [community firmware](https://github.com/SynthstromAudible/DelugeFirmware). Upstreaming isn't a goal of this fork (see `AGENTS.md`), so nothing here is promised.

Add an entry when you fix firmware code that isn't specific to Generative mode. Give the fix, where it is, why it's better, and its status.

| Fix | Where | Why it's better | Status |
| --- | --- | --- | --- |
| Null check before reading `clip->type` when `setup()` has neither a sound nor a clip | `src/deluge/gui/ui/sound_editor.cpp:2161` (`v1.3.0`) | It reads through a null `clip`. A root UI that isn't a clip view (such as Perform) can reach this path: Perform's own menus call `setup(nullptr, menu)` | Fixed in the fork (found by the test builds' null guard, [#115](https://github.com/gismya/deluge-generative/issues/115)) |
| `currentSong` → `song` in `loadInstrumentFromFile` | `src/deluge/storage/storage_manager.cpp:406` (`v1.3.0`) | Drums file their ParamManagers with `song`, but the check reads `currentSong`. Loading a KIT preset into a song that isn't current returns `FILE_CORRUPTED`, and with no current song it dereferences null. Every caller today passes the current song. Still present on upstream `main` | Not fixed in the fork. v1 doesn't need it; it belongs to the whole-card-kit future feature (see [Building Generator Kits in code](https://github.com/gismya/deluge-generative/issues/28)) |
| Bound the sysex firmware load progress bar to the pad grid (`loadProgressPad()`) | `src/deluge/io/midi/sysex.cpp:172` (`v1.3.0`), `src/deluge/io/midi/sysex_load_progress.h` | It divides by 64 KB less than the load buffer, so the last ~3% of an upload writes past `PadLEDs::image`. Builds that link live state such as `numUIsOpen` right after it crash near the end of the load ([#55](https://github.com/gismya/deluge-generative/issues/55)). Still present on upstream `main` | Fixed in the fork |
| Destruct the two edge FileItems that `deleteFolderAndDuplicateItems()` drops | `src/deluge/gui/ui/browser/browser.cpp:435` (`v1.3.0`) | It removes them with a bare `fileItems.deleteAtIndex()`, so their filename Strings are never released: 96–104 B of external heap lost on each preset search in a folder too big to list at once, such as every SHIFT+LOAD → NEW (`Song::ensureAtLeastOneSessionClip()`). Found by the enter/leave leak check ([#167](https://github.com/gismya/deluge-generative/issues/167)). The fix calls `~FileItem()` on each before the same `deleteAtIndex()`, and skips both when the list is empty. Still present on upstream `main` | Fixed in the fork |
| `AudioFileManager::deleteAllUnusedAudioFiles()`: one loop that deletes every AudioFile with no reasons to be loaded | `src/deluge/storage/audio/audio_file_manager.cpp:126,150` (`cardReinserted()`, `v1.3.0`) | `cardReinserted()` had the same delete-while-iterating loop twice, each mixed with its per-Sample checks and an `e--`. The helper runs first, then each check loops over what's left | Done in the fork (refactor only, no behaviour change) |
| The gold-knob popup names a MIDI CC from the Output on the knobs (`View::knobsOutput()`), not from the Song's current Clip | `src/deluge/gui/views/view.cpp:1132` (`displayModEncoderValuePopup()`, `v1.3.0`) | In a clip context it read `getCurrentOutputType()`/`getCurrentOutput()`, so the CC name came from the wrong Output whenever the knobs sit on another Clip than the current one, and a view with no current Clip dereferenced null. On the Deluge a null read returns whatever the empty CS0 bus floats to, so it crashed only sometimes: Perform froze after about 40 s of knob turns ([#115](https://github.com/gismya/deluge-generative/issues/115)) | Fixed in the fork |
| `usb_peri_devdefault()` writes the other-speed table's descriptor type only when there is one, and the high-speed path falls back to the configuration table without one | `src/RZA1/usb/r_usb_basic/src/driver/r_usb_pdriver.c:1309` (`v1.3.0`) | A driver may register no high-speed table (the Deluge registers `p_config_h = 0`). The full-speed path then wrote the null high-speed table at address 1 on every bus reset, and the high-speed path would read its length from address 2. Harmless on the Deluge (nothing on CS0), fatal under a null guard. Found at boot in delugemu by the test builds' null guard | Fixed in the fork |
| `SoundEditor::getCurrentModelStack()` reads the current Clip and Instrument only on a clip-minder screen | `src/deluge/gui/ui/sound_editor.cpp:2307` (`v1.3.0`) | It read both before checking, then used neither at song level, so a song-level menu with no current Clip dereferenced null on every render. Found by the test builds' null guard in Perform's menus | Fixed in the fork |
| Stop every DMA channel before a chainload (`chainload_from_buf()`) and at the top of `resetprg()` (`dmaStopAllChannels()`) | `src/deluge/util/chainload.cpp:50`, `src/resetprg.c:131` (`v1.3.0`), `src/deluge/drivers/dmac/dmac.c` | The chainloader masked IRQs and stopped four timers but left DMA running. The SSI, PIC, MIDI and MIDI-timing channels re-read their `const` link descriptors (in `.rodata`) at the end of every block, so once the copy overwrote them each channel loaded the new image's bytes as a descriptor and wrote where they pointed, into the new firmware's `.text`. Boots after a sysex firmware load (`loadfw`) crashed now and then, depending on the layout. A boot from the SD card is safe. Seen on the Deluge: the SSI TX channel was found running on a garbage descriptor at boot ([#166](https://github.com/gismya/deluge-generative/issues/166)). Still present on upstream `main` | Fixed in the fork |
| `getCurrentInstrumentClip()`, `getCurrentAudioClip()`, `getCurrentOutput()`, `getCurrentKit()` and `getCurrentOutputType()` return nullptr (or `OutputType::NONE`) with no current Clip, as `getCurrentInstrument()` already did | `src/deluge/model/song/song.cpp:82-134` (`v1.3.0`) | They dereferenced the current Clip unchecked, and the sound editor's song-level paths call them (the shortcut overlay, `editingKit()`, `shouldEditKitAffectEntire()`), so any song-level editor with no current Clip read null. Session view gets away with it because its current Clip is the last one opened, which is the wrong Clip to ask anyway. Found by the test builds' null guard when the sound editor opened over Perform ([#116](https://github.com/gismya/deluge-generative/issues/116)) | Fixed in the fork |
| The sound editor's null checks for a song-level session: `shouldEditKitAffectEntire()` reads `affectEntire` only from an InstrumentClip, a grid shortcut skips the note-row-editor check without a current Clip, and MIDI learn on a gold knob learns nothing without a current Output | `src/deluge/gui/ui/sound_editor.cpp:402, 1661, 1919` (`v1.3.0`) | Each dereferenced the current Clip or Output in a song-level menu. In session view MIDI learn took the gold knob's F page from the last Clip's Output, not the song's ([#116](https://github.com/gismya/deluge-generative/issues/116)) | Fixed in the fork |
