# Upstream candidates

These are firmware fixes, made in this fork or found while working on it, that look better than upstream's code whatever Generative mode needs. Each one should be checked for an upstream PR to the [community firmware](https://github.com/SynthstromAudible/DelugeFirmware). Upstreaming isn't a goal of this fork (see `AGENTS.md`), so nothing here is promised.

Add an entry when you fix firmware code that isn't specific to Generative mode. Give the fix, where it is, why it's better, and its status.

Still present on upstream `main` | Not fixed in the fork. v1 doesn't need it; it belongs to the whole-card-kit future feature (see [Building Generator Kits in code](https://github.com/gismya/deluge-generative/issues/28)) |

The fix calls `~FileItem()` on each before the same `deleteAtIndex()`, and skips both when the list is empty. Still present on upstream `main` | Fixed in the fork |

| The gold-knob popup names a MIDI CC from the Output on the knobs (`View::knobsOutput()`), not from the Song's current Clip | `src/deluge/gui/views/view.cpp:1132` (`displayModEncoderValuePopup()`, `v1.3.0`) | In a clip context it read `getCurrentOutputType()`/`getCurrentOutput()`, so the CC name came from the wrong Output whenever the knobs sit on another Clip than the current one, and a view with no current Clip dereferenced null. | `usb_peri_devdefault()` writes the other-speed table's descriptor type only when there is one, and the high-speed path falls back to the configuration table without one | `src/RZA1/usb/r_usb_basic/src/driver/r_usb_pdriver.c:1309` (`v1.3.0`) | A driver may register no high-speed table (the Deluge registers `p_config_h = 0`). | `SoundEditor::getCurrentModelStack()` reads the current Clip and Instrument only on a clip-minder screen | `src/deluge/gui/ui/sound_editor.cpp:2307` (`v1.3.0`) | It read both before checking, then used neither at song level, so a song-level menu with no current Clip dereferenced null on every render. | Stop every DMA channel before a chainload (`chainload_from_buf()`) and at the top of `resetprg()` (`dmaStopAllChannels()`) | `src/deluge/util/chainload.cpp:50`, `src/resetprg.c:131` (`v1.3.0`), `src/deluge/drivers/dmac/dmac.c` | The chainloader masked IRQs and stopped four timers but left DMA running. The SSI, PIC, MIDI and MIDI-timing channels re-read their `const` link descriptors (in `.rodata`) at the end of every block, so once the copy overwrote them each channel loaded the new image's bytes as a descriptor and wrote where they pointed, into the new firmware's `.text`. Boots after a sysex firmware load (`loadfw`) crashed now and then, depending on the layout. A boot from the SD card is safe. Seen on the Deluge: the SSI TX channel was found running on a garbage descriptor at boot ([#166](https://github.com/gismya/deluge-generative/issues/166)). A channel still active after the bounded wait keeps its status: it isn't reset under a transfer. Still present on upstream `main` | Fixed in the fork |

Session view gets away with it because its current Clip is the last one opened, which is the wrong Clip to ask anyway. Found by the test builds' null guard when the sound editor opened over Perform ([#116](https://github.com/gismya/deluge-generative/issues/116)) | Fixed in the fork |

| `renderOsc()`'s two `renderOscSync()` calls always render into `oscSyncRenderingBuffer` (it has 4 samples of room past its end), then `takeOscSyncRender()` adds it at the amplitude or copies it out | `src/deluge/dsp/oscillators/oscillator.cpp:428,476` (`renderOsc()`, `v1.3.0`) | Their storage lambdas store 4 samples at a time with `vst1q_s32` from wherever a sync lands, so they can write up to 3 samples past the window. Copying out is cheaper than the amplitude pass at 0 it replaces for that case. The wavetable path is untouched: `WaveTable::render()` stores one sample at a time and stops at the window's end. Still present on upstream `main` | Fixed in the fork |
